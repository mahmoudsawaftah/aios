# نموذج تشغيل شركة البرمجيات — AIOS Software Factory

## الرؤية
منصة متعددة المشاريع، فيها مالك بشري وطبقة إدارة أعمال وطبقة تنفيذ هندسي آلية. الغرض ليس الاستغناء عن الرقابة البشرية، بل تقليل الوقت اللازم لتحويل فكرة أو طلب عميل إلى منتج قابل للفحص والنشر.

## الوظائف الأساسية للشركة

| الوظيفة | المسؤولية | حالة أتمتتها في الإصدار الأول |
|---|---|---|
| Business Development | اكتشاف فرص العملاء والتأهيل | مخطط، غير منفذ |
| Sales / Proposals | عروض السعر والنطاق والعقود | مخطط، غير منفذ |
| Product Management | متطلبات السوق وقيمة المنتج | مدعوم بدور Discovery |
| Business Analysis | User stories والمواصفات | مدعوم بدور Requirements |
| PMO / Project Manager | المراحل والموارد والمخاطر | مدعوم جزئياً بدور Backlog |
| UX/UI Design | تصميم التجربة والواجهات | مخطط كدور مستقل |
| Software Architecture | عقود API وقاعدة البيانات والمعمارية | مدعوم بدور Architecture |
| Software Engineering | تطوير Backend / Frontend / Mobile | دور Implementation عام، وليس عمالاً متخصصين بعد |
| QA / Testing | Unit / Integration / E2E | دور QA؛ لا يوجد ضمان بعمل كل الاختبارات |
| Cybersecurity | مراجعة الثغرات والصلاحيات | دور Security للقراءة فقط |
| DevOps / SRE | بيئات staging/production والمراقبة | دور Release Plan فقط، لا يوجد نشر آلي |
| Customer Success | بلاغات العملاء والتدريب وSLA | مخطط، غير منفذ |
| Finance / Legal | الفوترة والتعاقد والامتثال | مخطط، غير منفذ |
| Documentation | مخرجات التسليم الفنية والعميل | إلزامي في مخرجات كل مرحلة |

## نظام قبول طلب مشروع جديد
1. يكتب المالك طلباً يحدد المشكلة، المستفيدين، الميزانية والمخرجات.
2. يقوم Discovery بعمل دراسة فرضيات وجدوى ومخاطر.
3. يحوّل Requirements الطلب إلى قصص مستخدم وقبول قابل للاختبار.
4. يحدّد Architecture الحدود الأمنية والتقنية والقرارات صعبة التراجع.
5. يبني Backlog تقسيم العمل وتقديرات تقريبية مع شروط الاكتمال.
6. **Owner Gate:** لا يبدأ تعديل الكود قبل مراجعة المالك.
7. ينفّذ Implementation داخل Worktree مستقل عن نسخة المشروع الأصلية.
8. يفحص QA وSecurity ما تم إنجازه بالفعل، وليس ما يُفترض أنه أُنجز.
9. يكتب Release Plan الخطوات والمخاطر والـRollback.
10. **Owner Gate:** تقرير مراجعة وموافقة قبل أي إجراء خارجي (دمج/نشر/إنتاج).

## إيقاع Agile / Traditional
- **Traditional:** عقد العمل، معايير القبول، الخصوصية، بنية البيانات والموافقات.
- **Agile:** تطوير الواجهات والخصائص على Sprints قصيرة، مع مراجعة كل Sprint وترتيب الأولويات.
- **Hybrid:** نقطة اعتماد قبل التطوير، والتنفيذ بالتكرار. التغييرات على النطاق أو الصلاحيات تحتاج موافقة واضحة.

## سلم النضج
- **النسخة 0 (المشمولة في هذا التحديث):** مهمة واحدة، ثمانية أدوار متتابعة، SQLite، ملف سجل وأدلة، Worktree منفصل، بوابتا موافقة، وسيلة استئناف يدوية / قابلة للجدولة.
- **النسخة 1:** Agent supervisors مستقلون؛ مهام متعددة مع قوائم انتظار وميزانيات/Timeout؛ اختبارات موثقة؛ Pull Requests آلية دون دمج.
- **النسخة 2:** لوحة متابعة، مراقبة التكاليف، ترتيب الأولويات، إدخال عملاء، تقرير جودة، تكاملات مشاريع GitHub.
- **النسخة 3:** عمّال في حاويات مع حدود موارد وشبكات وأسرار؛ أتمتة نشر Staging؛ موافقات بشرية للإنتاج؛ تشغيل قابل للاستعادة على أكثر من جهاز.

## مقاييس النجاح
- مدة تحويل الطلب إلى نموذج تجريبي، وعدد Stories المكتملة بمعايير القبول.
- نسبة اجتياز CI، معدل عودة العيوب، زمن معالجة الثغرات المهمة.
- نسبة نجاح استكمال المهام بعد الانقطاع، نسبة التدخل البشري المطلوبة.
- تكلفة النماذج لكل Story ومعدل استخدام الموارد، وعدد النسخ الاحتياطية التي تم اختبار استعادتها.

**حدود صريحة:** هذا الملف خطة تشغيل، وليس دليلاً على تنفيذ أقسام الشركة المخطط لها. لا تُرسل بيانات عميل أو تنفّذ معاملات مالية من خلال Agents حتى وجود سياسات مؤسسية وصلاحيات فعلية.
